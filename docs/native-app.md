# Is Dioxus the Right Framework for a Linux CNC Sender in Rust?

## TL;DR
- **Dioxus can technically build this app, but it is the wrong tool for a real-time CNC sender on Linux.** Its desktop renderer embeds the WebKitGTK webview (via Tao + Wry), which on Linux brings heavy native dependencies, well-documented rendering bugs (black screens, Nvidia compositing issues), slow cold-start, and the latency/overhead of marshaling state through a browser engine — exactly the friction you do not want on a hardware-control tool that must reliably inject real-time bytes.
- **The recommended choice is egui (eframe), with iced as a close second.** egui is fully native Rust (no webview), has the strongest Linux track record, and there is existing prior art of serial-monitor and CNC/G-code tools built with it. iced has the cleanest async/streaming story (its `Subscription` model maps almost perfectly onto a grblHAL serial read/stream loop) if you prefer a structured Elm architecture over immediate mode.
- **Whatever the UI, isolate the serial/streaming engine into its own crate** built on `tokio-serial` (or `serial2-tokio`) plus a hand-written character-counting state machine, and communicate with the UI over channels. This decoupling means the GUI framework is a swappable detail, which de-risks the decision considerably.

## Key Findings

**1. Dioxus desktop on Linux = a WebKitGTK webview, not a native renderer.** The stable desktop renderer (`dioxus-desktop`, current stable line 0.7.x as of mid-2025, with 0.6 the prior stable branch) uses the Tao window manager and Wry webview, embedding WebKitGTK on Linux. This requires system packages such as `libwebkit2gtk-4.1-dev`, `libgtk-3-dev`, `libsoup-3.0-dev`, and `libxdo-dev`. A Rust-native alternative, **Dioxus Native (Blitz + Vello/WGPU)**, exists but is explicitly **experimental** — it ships in 0.7 but is described by the maintainers as young and missing many event types and widgets. So as a practical matter, a Dioxus desktop app you ship in 2025 is a webview app.

**2. Documented Linux pain points are real.** Community guides describe an "infamous black screen bug on Linux," sometimes worked around by setting `WEBKIT_DISABLE_COMPOSITING_MODE=1`. There are open issues for blank screens after `dx serve`, black screens on minimize/maximize, transparency rendering glitches, small/blurry text under WebKitGTK on NixOS/Wayland, and slow first-paint/startup time attributed to WebKitGTK (one launcher author reported up to ~10-second cold starts on slower hardware). WebKitGTK itself has a long-standing rendering bug on Nvidia proprietary drivers. None of these are fatal, but they are the kind of environment-specific instability that is poison for a tool that controls a physical machine.

**3. Async story: Tokio is present, but Dioxus's own runtime is single-threaded.** On desktop, Dioxus uses Tokio to drive futures, but its `spawn`/`use_future`/`use_coroutine` tasks all run on the **main UI thread** — the docs explicitly warn that a blocking or CPU-heavy task will freeze the UI, and recommend `std::thread::spawn` or a separate Tokio task for anything long-running or blocking. To update UI state from a real background thread you must use `use_signal_sync` (the `Send + Sync` `SyncStorage` signal), because the default signal and Dioxus's own `spawn` are not thread-safe. This works, but it is a notable constraint and a sharp edge for newcomers.

**4. Serial crates are mature and framework-independent.** `serialport-rs` (blocking I/O, port enumeration with USB metadata via libudev on Linux) is the de-facto base; `tokio-serial` (5.4.5, MSRV 1.46.0) wraps it for async with `SerialStream` — per docs.rs/tokio-serial, "Reading and writing to a SerialStream is usually done using the convenience methods found on the tokio::io::AsyncReadExt and tokio::io::AsyncWriteExt traits." `serial2-tokio` is a newer, simpler cross-platform async option; per crates.io it notes "The SerialPort struct implements the standard tokio::io::AsyncRead and tokio::io::AsyncWrite traits, as well as read() and write() functions that take &self instead of &mut self. This allows you to use the serial port concurrently from multiple tasks," and provides `SerialPort::available_ports()` for enumeration. Note `serialport-rs` is explicitly seeking maintainers (especially for Windows), but for Linux USB-CDC it is solid and widely used. The grblHAL/Grbl character-counting protocol is well-specified: per the gnea/grbl official "Grbl v1.1 Interface" wiki, "We know Grbl has a 128 character serial receive buffer, and the host PC can send up to 128 characters without overflowing the buffer" (the reference `stream.py` defines `RX_BUFFER_SIZE = 128`). You track bytes sent vs. that buffer, decrement on each `ok`/`error`, and inject real-time single-byte commands like `?`, `!`, `~`, `0x18` out-of-band. (Note: 128 is *legacy* Grbl; grblHAL on a 32-bit MCU advertises a larger buffer — Galdr reports **1024** — so the built `skirnir` engine defaults to 1024 and refines from the controller's `[OPT:...]` reply at connect; see `crates/skirnir/src/protocol/flow.rs` `DEFAULT_RX_BUFFER`.) This maps naturally onto an async read loop + a send-ahead loop coordinated by channels.

**5. Prior art strongly favors native-Rust GUIs for this exact use case.** Real serial/CNC tools in Rust use egui or Slint, not Dioxus: `serial-monitor-rust` (egui) and `SerialGUI-rs` (eframe + serialport-rs) are shipping serial monitors; `gcodekit4` is a Rust UGS-style grblHAL/Grbl sender built on **Slint**; `visualgcode` is a G-code toolpath visualizer built on **egui + wgpu** rendering 100k+ segments at 60 FPS. For Dioxus specifically, the only concrete serial example I found is a 2023 rust-lang forum thread that ended without a fully working background-read architecture — telling, given how common this task is.

## Details

### Dioxus desktop maturity on Linux (2025)
Dioxus reached 0.7 in the 2025 cycle (the 0.7 polish phase ran roughly six months longer than planned, through ~nine alpha/pre-releases), with 0.8 now in early development focused on native APIs and bug-squashing. The maintainers themselves acknowledge this in the official 0.7 docs ("Next Steps"): "Dioxus is quite a large project and has been a bit slower to mature than other projects with larger development teams or smaller scopes. With 0.6, Dioxus is more mature but still has some ground to cover." Desktop rendering on Linux is WebKitGTK via Wry/Tao. The experimental Blitz/Vello native renderer is the long-term answer to the webview's weight but is not production-ready for a complex app in 2025 — its CSS support matrix is incomplete and widget/event coverage is partial.

Production usage exists (Huawei has shipped production apps; Airbus/ESA and Satellite.im are cited adopters), and the project is well-funded with an active Discord and 24.5k GitHub stars (per the dioxuslabs.com header). It is not abandonware. But note the community-app ecosystem is still thin — the flagship Dioxus-based desktop app (Satellite.im's "Uplink" P2P chat) sits in the low hundreds of stars — and "production-ready for web/cross-platform content apps" is different from "appropriate for a latency-sensitive Linux hardware-control tool."

### Async integration for a streaming loop
The architecture that works in Dioxus: run the serial read loop and the streaming send-ahead loop on a dedicated Tokio task or OS thread (never on the UI thread), use a `use_coroutine` to receive commands from the UI via its channel handle, and push machine state (position, status, ok/error events, progress) back to the UI through `use_signal_sync` signals or an mpsc channel drained by a small polling task. This is viable. The friction is that you are constantly working around the single-threaded UI runtime and the read-only-by-default state model. The one documented real-world attempt (a 2023 rust-lang forum thread) is instructive: the developer stored a `Box<dyn SerialPort>` in component props and immediately hit a borrow-checker error ("cannot borrow `cx.props.port` as mutable, as it is behind a `&` reference"). The verified working fix was wrapping the port in a `RefCell` for interior mutability; the "proper" architecture (a `use_coroutine` + `use_context` + command-enum channel, with reads pushed back through signals) was described conceptually but **never confirmed working** in the thread, and the helper self-identified as not knowing serialport or Dioxus well. Maintainers separately confirm the key constraint in discussion #2261: "In dioxus, spawn is single threaded. If you need a sync signal for a tokio task, you can use_sync_signal." Dioxus's own intro blog endorses the general pattern — "your Dioxus code will run on its own thread... you can access hardware, file system, and platform APIs directly... platform access occurs inside an asynchronous multithreaded coroutine" — but its bundled examples are a file explorer and a WiFi scanner, not serial.

### State management
Dioxus signals (0.5+) are `Copy`, ergonomic, and support fine-grained reactivity; `use_context_provider`/`use_context` gives you a global store, and `use_signal_sync` gives thread-safe signals (backed by an `RwLock` `SyncStorage`, vs. the default `RefCell` `UnsyncStorage`). For a CNC sender's shared state (DRO position, connection status, streaming progress, settings map, alarm state) this is more than adequate and arguably pleasant. State management is not where Dioxus falls down — rendering and platform stability are.

### GCode file handling and large lists
Parsing thousands of G-code lines off the UI thread is trivial in any of these frameworks. The concern with Dioxus is **rendering** a long, live-updating line list with current-line highlighting: this means many DOM nodes in WebKitGTK. Dioxus does offer a virtualized-list component in its component library, and there is a known issue (#3076) of large-list rendering being slow on some webview engines (a ~2000-item tree took 20–30 s to expand on Safari/WebKit while being instant on Chrome/Firefox). In egui you would draw only visible rows immediate-mode; in iced you would use a scrollable with lazy elements. Both avoid the DOM-node explosion.

### Specific features
- **File picker:** `rfd` (Rusty File Dialogs) is the standard cross-platform native dialog crate and works with any of these frameworks; on Linux it uses the XDG Desktop Portal (default) or a GTK3 backend. egui and iced integrate with it directly; Dioxus can call it too.
- **Port enumeration:** `serialport::available_ports()` (or the tokio-serial / serial2-tokio equivalents) lists ports with USB VID/PID metadata on Linux via libudev.
- **Scrolling console/log:** trivial and efficient in egui/iced; in Dioxus, watch for DOM growth — cap the buffer.
- **Settings form from `$$` dump:** a dynamic key-value list binds cleanly to reactive state in all three; this is a non-issue.
- **2D toolpath preview (future):** This is the decisive future requirement. egui has first-class custom 2D painting (`Painter`) and integrates with wgpu for GPU-accelerated paths (see `visualgcode`); iced has a `Canvas` widget purpose-built for this; Slint has a renderer for custom graphics. In Dioxus you would render SVG or an HTML `<canvas>` inside the webview and drive it with JS interop — workable but the least natural and least performant path of the options.

### Honest framework comparison for a Linux-first CNC sender

- **egui (eframe) — RECOMMENDED.** Immediate-mode, 100% native Rust over OpenGL/wgpu, no webview, smallest binaries, excellent Linux support, used in shipping serial monitors and G-code visualizers. Async integration is manual but simple: run Tokio in a background thread, push state via channels, call `ctx.request_repaint()`. Downsides: immediate-mode means you redraw each frame (CPU/GPU usage you can throttle), basic theming, non-native look. For a CNC sender — a dense, custom, real-time dashboard with a toolpath canvas — immediate mode is a genuinely good fit.
- **iced — RECOMMENDED ALTERNATIVE.** Retained-mode, Elm architecture, pure Rust, no webview, native wgpu rendering, reactive (no longer redraws constantly since 0.14). Its **`Subscription`** primitive is essentially built for this: `Subscription::run` spawns a background stream (e.g. your serial connection), the documented websocket example shows the exact channel-handshake pattern you need for bidirectional serial comms, and a built-in `Canvas` widget handles toolpath preview. Production credibility is strong: per System76 engineer Michael Murphy (quoted by Phoronix), "After much deliberation and experimentation over the last year, the engineering team has decided to use Iced instead of GTK" — System76's COSMIC desktop shipped stable (Epoch 1) with Pop!_OS 24.04 LTS, built in Rust on iced and libcosmic; Kraken also ships an iced desktop app. Caveats: it's largely a one-maintainer project, the API changes between releases, and you must run it inside a Tokio context.
- **gtk4-rs.** Mature native Linux widgets, excellent Linux integration, GObject-based async with the `glib` main context (integrates with Tokio via channels). Most "native Linux" look. Downsides: GTK/GObject paradigm is heavier and less idiomatic Rust; more boilerplate; cross-platform later is harder. A reasonable choice if Linux-native look is paramount.
- **Slint.** Declarative `.slint` markup + Rust backend, native rendering, proven for exactly this use case (`gcodekit4`). Async via `slint::spawn_local` + a background Tokio runtime, bridging back with `invoke_from_event_loop`. Caveat: **licensing** — Slint is GPL/royalty or a paid commercial license for closed-source; fine if your project is GPL or you buy a license, a blocker otherwise. Its async-from-UI ergonomics have been a documented friction point (one user explicitly switched to iced over it, calling iced "a good bit more async-friendly").
- **Tauri v2.** Same WebKitGTK webview weight as Dioxus on Linux, but its frontend is web-first. A "Rust-only frontend" means running Leptos/Yew/Dioxus compiled to WASM inside the webview — and even then you cannot fully escape JS glue, and you inherit all the WebKitGTK issues plus an IPC boundary between the WASM frontend and the Rust backend. For a developer who dislikes TypeScript and wants Linux-native reliability, Tauri offers the worst of both worlds here. Tauri itself notes Dioxus has its own webview stack (wry/tao) and doesn't need Tauri.

### Why not Dioxus, concretely
The CNC sender's hard requirements are (a) rock-solid Linux desktop behavior, (b) reliable real-time serial I/O with low jitter, and (c) a future GPU-friendly 2D toolpath canvas. Dioxus's webview architecture works against all three: it adds the WebKitGTK dependency and its Linux rendering bugs, it forces hardware I/O through a single-threaded UI runtime plus interior-mutability workarounds, and it pushes 2D drawing into JS/canvas interop. None of these are dealbreakers individually, but collectively they make Dioxus a high-friction choice for precisely the parts that matter most — while offering its main advantages (HTML/CSS styling, web+mobile from one codebase) that this Linux-only desktop tool does not need.

## Recommendations

**Stage 1 — Build the engine first, framework-agnostic (do this regardless of UI choice).**
Create a `cnc-core` crate with: serial transport on `tokio-serial` (fall back to `serial2-tokio` if you want simpler concurrent read/write via `&self`), a character-counting streaming state machine (track sent bytes against the 128-byte grblHAL RX buffer), an `ok`/`error`/status-report parser, a real-time command injector, and a typed `enum` command channel in / `enum` event channel out. Build a headless CLI test harness that streams a file to your ESP32-S3. This validates the hardest, highest-risk part with zero GUI dependency and makes the UI framework swappable. Follow the grblHAL "For sender developers" startup guidance (don't assume a hard reset or welcome message on native-USB connect; listen briefly for status reports to detect an active MPG before taking control).

**Stage 2 — Build the UI in egui (eframe).** Wire the GUI to `cnc-core` purely over channels; call `ctx.request_repaint()` when events arrive. Implement: port-enumeration dropdown (`serialport::available_ports`), `rfd` file picker, a capped scrolling console, a current-line-highlighted G-code list (draw visible rows only), a DRO/status panel, and a settings form bound to the `$$` map. egui gives you the fastest path to a dense, responsive, native tool with no webview surprises.

**Stage 3 — Toolpath preview & probing.** Use egui's `Painter` for a first 2D preview; move to an egui+wgpu custom paint callback (cf. `visualgcode`) if you need to render large files at 60 FPS. Add Z-probe/touch-plate flows as new command-channel messages — no UI-architecture change required.

**Decision thresholds — when to revisit Dioxus:**
- Choose **iced instead of egui** if you strongly prefer a structured, message-driven Elm architecture and want the `Subscription`/`Canvas` model — it is equally appropriate here.
- Reconsider **Dioxus** only if (a) you later need to ship the *same* UI to web or mobile, **and** (b) Dioxus Native (Blitz) reaches stable, non-experimental status with full event/widget and canvas support on Linux. Until Blitz is production-ready, the webview tax isn't worth it for a Linux hardware tool.
- Consider **Slint** if a fully native-looking declarative UI matters and your licensing situation (GPL or commercial license) is compatible — `gcodekit4` proves the exact use case is achievable.

## Caveats
- **Versions move fast.** Dioxus was in its 0.7 stable cycle with 0.8 in early development as of mid-2025; iced's reactive-rendering and API details referenced here are from its 0.14 line; these ecosystems change quickly, so re-verify current status before committing.
- **The "Dioxus is unsuitable" verdict is a judgment call, not an absolute.** People have shipped production Dioxus desktop apps. The recommendation against it is specific to a *latency-sensitive, Linux-only, hardware-control* tool — a context that maximizes Dioxus's weaknesses and ignores its strengths. For a content-style cross-platform app the calculus would flip.
- **`serialport-rs` is seeking maintainers**, primarily for Windows; the Linux USB-CDC path is stable and battle-tested, but track the project's health.
- **Real-time reliability also depends on the OS and USB stack**, not just the GUI: USB-CDC latency, kernel buffering, and the ESP32-S3's native-USB behavior (grblHAL may not hard-reset on connect over native USB, and may auto-emit status reports rather than the welcome message) all affect a sender.
- I could not find a single shipped, non-trivial Dioxus serial/hardware app to study, whereas egui and Slint each have concrete examples — absence of evidence here is itself weakly informative.
